# Критерии приёмки и тестовые сценарии

**Дата:** 10.11.2026 · **Объект:** MVP-бот сообщества «Ясные очи».
**Статус:** код реализован, 83 юнит-теста пройдено (включая mock-проверку ошибок API и
перезапуска). 11.11.2026 выполнен короткий smoke-запуск: процесс поднялся, LongPoll
подключился. Ручная проверка сценариев в клиенте ВКонтакте **не выполнялась**.

## 1. Как пользоваться документом

- Каждый критерий имеет ID `AC-01`…`AC-18` и ссылку на требования из
  [`requirements.md`](requirements.md).
- «Предусловие» описывает состояние до шага; «Шаги» — действия тестировщика в клиенте
  ВКонтакте; «Ожидаемый результат» — наблюдаемое поведение.
- **P0** — без прохождения MVP не принимается. **P1** — важно, допускается исправление
  в первой итерации после запуска.
- Проверка выполняется на тестовом сообществе с тестовым токеном. Реальные пользователи
  не участвуют.
- Результат фиксируется: дата, тестировщик, версия каталога, скриншот или текст ответа.

`[РЕШЕНИЕ]` Все критерии ниже — P0, кроме явно отмеченных P1.

## 3. Сценарии

### AC-01. Первый запуск и главное меню — P0

**Требования:** FR-01, FR-02.
**Предусловие:** пользователь ранее не писал боту; каталог валиден; процесс запущен.

**Шаги:**

1. Открыть диалог сообщества.
2. Нажать «Начать».
3. Нажать «Начать» повторно (если кнопка доступна) или отправить «привет».

**Ожидаемый результат:**

- приходит приветствие из [`dialogues.md`](dialogues.md), раздел 5.1;
- под сообщением — клавиатура: «Услуги», «Прайс-лист», «Связаться с менеджером»;
- нет запроса имени, телефона, e-mail и других персональных данных;
- повторный запуск показывает то же меню, без ошибок и дублей приветствия в одном ответе.

### AC-02. Список услуг — P0

**Требования:** FR-03.
**Предусловие:** открыто главное меню.

**Шаги:**

1. Нажать «Услуги».

**Ожидаемый результат:**

- одно сообщение со списком;
- ровно 10 кнопок услуг, подписи совпадают с полем `button` каталога;
- порядок совпадает с `sort_order`;
- есть кнопки «К списку услуг» и «В главное меню»;
- ни одна подпись не длиннее 40 символов;
- в сообщении есть оговорка об ориентировочных ценах.

### AC-03. Карточка услуги — P0

**Требования:** FR-04.
**Предусловие:** открыт список услуг.

**Шаги:**

1. Нажать «Проверка зрения для очков».
2. Вернуться к списку.
3. Открыть «Лазерная сварка».
4. Открыть «Ультразвуковая чистка».

**Ожидаемый результат для каждой карточки:**

- название, цена с единицей, полное описание, список «Что входит», список «Важно»;
- цена и текст совпадают с [`services.md`](services.md) и `catalog/services.json`;
- есть дисклеймер «Цены ориентировочные, не являются публичной офертой»;
- нет обещаний лечения, гарантии результата и медицинских советов;
- клавиатура: «К списку услуг», «В главное меню», «Связаться с менеджером»;
- сообщение укладывается в лимит одного сообщения ВКонтакте.

### AC-04. Прайс-лист — P0

**Требования:** FR-05, FR-06.
**Предусловие:** открыто главное меню.

**Шаги:**

1. Нажать «Прайс-лист».
2. Сравнить каждую строку с карточкой соответствующей услуги.
3. Нажать «К услугам».
4. Нажать «В главное меню».

**Ожидаемый результат:**

- в прайсе все 10 услуг, порядок как в каталоге;
- формат цены: `2 500 ₽` для фиксированной и `от 1 300 ₽` для «от»;
- строка цены в прайсе **посимвольно** совпадает со строкой цены в карточке;
- есть дата/регион и дисклеймер;
- «К услугам» открывает список, «В главное меню» — меню;
- повторное открытие прайса даёт тот же результат.

### AC-05. Возврат и навигация — P0

**Требования:** FR-07, FR-08.
**Предусловие:** бот запущен.

**Шаги:**

1. Меню → «Услуги» → карточка → «К списку услуг» → «В главное меню».
2. Меню → «Прайс-лист» → «К услугам» → карточка → «В главное меню».
3. Из карточки нажать «Связаться с менеджером», затем «В главное меню».

**Ожидаемый результат:**

- каждый переход открывает ожидаемый экран;
- нет «тупиков»: с любого экрана есть путь в меню;
- нажатие «В главное меню» всегда работает, даже если экран был открыт давно;
- бот не требует вводить команды текстом.

### AC-06. Связь с менеджером — P0

**Требования:** FR-09, FR-10.
**Предусловие:** в `.env` задан корректный `MANAGER_CONTACT_URL`.

**Шаги:**

1. В главном меню нажать «Связаться с менеджером».
2. Нажать кнопку-ссылку «Написать менеджеру».
3. Вернуться в диалог бота.
4. Нажать «Я написал менеджеру».

**Ожидаемый результат:**

- экран содержит ссылку на диалог сообщества, объяснение, что отвечает человек, и график
  работы менеджера: 10:00–19:00 МСК в рабочие дни;
- кнопка-ссылка открывает указанный URL;
- после «Я написал менеджеру» приходит подтверждение с TTL;
- бот переходит в тихий режим (проверяется в AC-12);
- никакая заявка, имя или телефон не запрашиваются.

`[ВОПРОС]` В ответах Q-04 и Q-17 указаны две разные ссылки. До выбора единой ссылки
сценарий считается частично согласованным.

### AC-07. Неизвестный ввод — P0

**Требования:** FR-13.
**Предусловие:** тихий режим выключен.

**Шаги:**

1. Отправить «сколько стоит».
2. Отправить «лечите ли вы астигматизм».
3. Отправить пустое сообщение или стикер (если клиент позволяет).
4. Отправить длинный текст без команд.

**Ожидаемый результат:**

- приходит текст «Не понял сообщение» и главное меню;
- бот не угадывает услугу и не даёт медицинских рекомендаций;
- бот не падает и не отправляет несколько ответов на одно сообщение;
- в логе фиксируется факт неизвестного ввода без текста сообщения.

### AC-08. Устаревшие кнопки — P0

**Требования:** FR-14.
**Предусловие:** есть сообщение со старой клавиатурой; каталог изменён.

**Шаги:**

1. Нажать кнопку услуги, которая всё ещё существует.
2. Нажать кнопку с payload `{"v":1,"a":"svc","id":"removed_service"}`.
3. Нажать кнопку с payload `{"v":1,"a":"old_action"}`.
4. Нажать кнопку с payload без поля `v`.
5. Отправить повреждённый payload (если возможно воспроизвести).

**Ожидаемый результат:**

| Шаг | Ожидание |
|---|---|
| 1 | открывается актуальная карточка |
| 2 | «Услуга не найдена» + список услуг |
| 3 | «Эта кнопка устарела» + главное меню |
| 4 | считается устаревшей, меню |
| 5 | бот не падает, меню или сообщение об устаревшей кнопке |

- процесс остаётся работоспособным после каждого шага;
- в логе есть действие и ID, но нет текста сообщения.

### AC-09. Конфигурация и секреты — P0

**Требования:** FR-15, NFR-06, NFR-12.
**Предусловие:** тестовый стенд.

**Шаги:**

1. Запустить бота без `VK_BOT_TOKEN`.
2. Запустить с пустым `VK_BOT_TOKEN`.
3. Запустить без `MANAGER_CONTACT_URL`.
4. Запустить с `MANAGER_CONTACT_URL=http://example.com`.
5. Запустить с `MANAGER_MODE_TTL_HOURS=0` и `=999`.
6. Запустить с `LOG_LEVEL=TRACE`.
7. Запустить с валидной конфигурацией и проверить логи.

**Ожидаемый результат:**

- в случаях 1–6 процесс завершается с кодом 2 и понятным сообщением;
- сообщение называет переменную, но **не** выводит её значение;
- в логах и трейсбеках нет токена, ключа LongPoll и содержимого `.env`;
- при валидной конфигурации процесс запускается и отвечает на сообщения;
- `.env` отсутствует в `git status`.

### AC-10. Ошибка API ВКонтакте — P0

**Требования:** FR-16.
**Предусловие:** бот запущен; есть способ смоделировать ошибку (неверный `peer_id`,
ограничение прав, тестовый обработчик).

**Шаги:**

1. Вызвать ошибку отправки сообщения.
2. Отправить корректное сообщение после ошибки.
3. Проверить лог.

**Ожидаемый результат:**

- процесс не завершается;
- в логе есть код ошибки и метод, но нет токена и текста сообщения;
- следующее корректное сообщение обрабатывается;
- пользователь не получает «сырой» трейсбек.

`[ПРЕДПОЛОЖЕНИЕ]` Ошибки прав токена (например, код 7 или 15) не исправляются автоматически;
бот продолжает работу, администратор видит ERROR в логе.

### AC-11. Перезапуск и сохранение состояния — P0

**Требования:** FR-17, FR-20.
**Предусловие:** бот запущен; пользователь вошёл в тихий режим.

**Шаги:**

1. Остановить процесс.
2. Запустить снова.
3. Отправить обычный текст от того же пользователя.
4. Нажать «В главное меню».
5. Повторить цикл при повреждённом `runtime/state.json`.

**Ожидаемый результат:**

- после перезапуска навигация работает;
- тихий режим сохраняется, пока TTL не истёк;
- «В главное меню» выключает тихий режим;
- при повреждённом файле бот пишет WARNING и работает без тихого режима;
- повторная обработка последнего события (при `skip_old_events=False`) не ломает сценарий;
- в репозитории нет `runtime/state.json` и `.vkbottle/`.

### AC-12. Тихий режим: молчание — P0

**Требования:** FR-11.
**Предусловие:** пользователь нажал «Я написал менеджеру».

**Шаги:**

1. Отправить «привет».
2. Отправить «сколько стоит».
3. Нажать кнопку услуги из старого сообщения.
4. Нажать кнопку «Прайс-лист» из старого сообщения.
5. Попросить второго тестировщика (роль менеджера) ответить в диалоге сообщества.
6. Нажать «В главное меню».

**Ожидаемый результат:**

- шаги 1–4 не вызывают ответа бота;
- ответ менеджера на шаге 5 не вызывает автоматической реакции бота: он не дублирует сообщение,
  не отправляет меню и не мешает переписке;
- шаг 6 выключает тихий режим и показывает меню;
- другие пользователи в это время получают обычные ответы;
- состояние не влияет на менеджера, который пишет в диалог.

`[РЕШЕНИЕ]` В тихом режиме игнорируются все действия, кроме `menu`. Это осознанно: иначе
бот снова начнёт мешать разговору.

### AC-13. Тихий режим: выход и TTL — P0

**Требования:** FR-12.
**Предусловие:** тихий режим включён; TTL можно задать малым значением для теста.

**Шаги:**

1. Установить `MANAGER_MODE_TTL_HOURS=1`, войти в тихий режим.
2. Дождаться истечения TTL (или изменить системное время / `until` в тестовом файле).
3. Отправить обычный текст.
4. Войти в тихий режим снова и нажать «В главное меню».

**Ожидаемый результат:**

- после TTL бот снова отвечает на обычный текст и показывает меню;
- запись о пользователе удаляется или игнорируется;
- явный выход работает до истечения TTL;
- повторный вход обновляет `until`, а не создаёт дубль;
- TTL по умолчанию — 12 часов.

### AC-14. Устойчивость payload и клавиатур — P0

**Требования:** NFR-09, FR-14.
**Предусловие:** тестовый каталог.

**Шаги:**

1. Проверить все payload: длина ≤ 255 символов, валидный JSON.
2. Проверить все подписи кнопок: длина ≤ 40 символов.
3. Нажать каждую кнопку в каждом экране.
4. Отправить payload с лишними полями.
5. Отправить payload с `v=2`.

**Ожидаемый результат:**

- все кнопки работают;
- лишние поля не мешают, если `v` и `a` корректны;
- `v=2` считается неизвестной версией и обрабатывается как устаревшая кнопка;
- нет кнопок с пустым текстом или дублирующимися подписями;
- клавиатура отображается в мобильном и десктопном клиенте.

### AC-15. Каталог и единый источник цены — P0

**Требования:** FR-05, FR-18, NFR-07.
**Предусловие:** доступ к `catalog/services.json`.

**Шаги:**

1. Проверить уникальность ID и `sort_order`.
2. Проверить обязательные поля у всех 10 услуг.
3. Изменить цену одной услуги в JSON, перезапустить бота.
4. Открыть карточку и прайс.
5. Внести заведомую ошибку: дубль ID, пустое название, `price=0`, `button` длиннее 40.
6. Запустить бота.

**Ожидаемый результат:**

- шаги 1–2 проходят без ошибок;
- после изменения цены карточка и прайс показывают новое значение одинаково;
- в случаях 5–6 процесс завершается с кодом 3 и указывает проблемное поле/ID;
- бот не запускается с невалидным каталогом и не показывает «старую» цену;
- тексты карточек не дублируются в коде.

### AC-16. Повторное обращение — P0

**Требования:** FR-01.
**Предусловие:** пользователь уже пользовался ботом; тихий режим выключен.

**Шаги:**

1. Закрыть диалог.
2. Открыть снова через некоторое время.
3. Отправить «меню».
4. Нажать «Начать».

**Ожидаемый результат:**

- на шаге 3 показывается главное меню без приветствия, а не прошлый экран;
- на шаге 4 показывается приветствие и главное меню — повторное приветствие допустимо;
- нет ошибок и дублирующих ответов;
- старые сообщения с кнопками продолжают работать по AC-08;
- состояние пользователя не восстанавливается, потому что оно не хранится.

### AC-17. Приватность и логи — P0

**Требования:** FR-19, NFR-05.
**Предусловие:** включено логирование `INFO`.

**Шаги:**

1. Пройти сценарии: меню, услуга, прайс, менеджер.
2. Проверить файл лога и консоль.
3. Проверить `runtime/state.json`.

**Ожидаемый результат:**

- в логах нет текста сообщений пользователя, имени, телефона, токена;
- есть `peer_id`, действие, ID услуги, коды ошибок;
- `runtime/state.json` содержит только `peer_id`, `until`, `set_at`;
- нет медицинских данных и истории переписки;
- файл состояния не коммитится.

`[ФАКТ]` 10.11.2026 владелец согласовал текущее хранение: только `peer_id` и время
тихого режима (Q-09). `peer_id` считается псевдонимизированным идентификатором.

`[ВОПРОС]` Журнал обращений на 30 суток ещё не реализован. Не решено, хранить только
метаданные (`peer_id`, время, действие) или тексты сообщений. До решения AC-17 проверяет
текущее состояние без журнала.

### AC-18. Конкурентность и идемпотентность — P1

**Требования:** NFR-03, NFR-01.
**Предусловие:** бот запущен.

**Шаги:**

1. Быстро нажать одну кнопку пять раз.
2. Одновременно нажать «Услуги» и «Прайс-лист» с двух устройств.
3. Дважды нажать «Я написал менеджеру».
4. Проверить время ответа.

**Ожидаемый результат:**

- бот не падает и не смешивает состояния;
- возможны дубли сообщений — это допустимо;
- тихий режим включается один раз, `until` обновляется;
- типовой ответ приходит менее чем за 1 секунду без учёта сети ВКонтакте;
- файл состояния остаётся валидным JSON.

## 6. Что не проверяется на приёмке

- реальные медицинские рекомендации — их нет в боте;
- фактическая доступность услуг в салонах — это организационное подтверждение, а не тест;
- оплата, запись, CRM — не входят в MVP;
- поведение при тысячах одновременных пользователей — вне границ MVP;
- корректность цен «Ясных очей» — цены проектные и требуют утверждения владельцем.

## 7. Форма фиксации результата

Для каждого критерия:

```text
AC-XX: пройден / не пройден / заблокирован
Дата: ГГГГ-ММ-ДД
Тестировщик:
Версия каталога: <updated_at>
Комментарий:
Доказательство: скриншот / фрагмент лога без секретов
```

`[РЕШЕНИЕ]` Дефекты классифицируются:

- **Blocker** — бот не запускается, теряет данные, раскрывает секрет;
- **Critical** — не работает обязательный сценарий или цена расходится;
- **Major** — неверный текст, сломанная кнопка, ложный тихий режим;
- **Minor** — опечатка, форматирование, неудобство.

Blocker и Critical блокируют запуск. Major исправляется до публикации, если затрагивает
деньги, медицинские формулировки или связь с менеджером.
